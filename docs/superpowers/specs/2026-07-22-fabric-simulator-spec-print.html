Fabric Simulator
System & API Specification

The complete design to turn the single-tenant configurator into a per-client web experience — each client logs in and sees only its own furniture and fabrics, used live during customer consultations. Includes the full architecture, a request-layer review of the existing code, and every API documented one by one.

Prepared for  Anviksha (Founder) Date  22 July 2026 Schema  simulator Host  web.simulator.livinit.ai
01

Overview

The simulator is a browser 3D configurator: a client's consultant picks a product, applies real fabrics to individual parts, stages it in a room and generates AI-photoreal renders — live in front of a customer. The v1 goal is to make it multi-tenant: many clients, each with a private library, one shared platform.

Private per client

Each account accesses only its own furniture & fabrics.

Login-gated

Consultants sign in; the session drives what they see.

Team-onboarded

Clients send 2D images + a fabric list; Livinit builds the 3D assets.

Dedicated host

Its own experience at web.simulator.livinit.ai.

The gap in one line

Today — single-tenant demo
  • One shared, public asset set
  • No login
  • Catalog compiled into JavaScript
  • Any client could read another's files
  • Uncapped AI spend
Target — per-client platform
  • Each account sees only its own library
  • Login required
  • Catalog served per-tenant from a database
  • Isolation in DB and asset proxy
  • Per-tenant AI quota
Decisions locked

Backend: standalone Supabase (Auth + Postgres + RLS). Tenant model: simulator-owned — its own Supabase, zero blast radius on the core backend (Option A). Onboarding: staff-only admin console. Reuse: auth patterns from web-pipeline + Livinit's existing Stripe credits for AI metering.

Tenant isolation — two independent locks

Lock 1 · Database (RLS)

Every query filtered by tenant_id = token.tenant_id in Postgres. Forget a filter and the DB still returns nothing.

Lock 2 · Asset proxy (prefix)

Every file must sit under tenants/<your id>/. Ask for another's key → 403 before S3 is touched.

The claim is set once, server-side

On sign-in a Supabase hook stamps tenant_id + role into the JWT from simulator.memberships. Every endpoint re-derives them from the verified token — the browser can never assert which tenant it is.

Storage — bucket simulator-assets

s3://simulator-assets/
  shared/                       # room shells — any authed tenant
  tenants/<tenant_id>/          # gated: prefix MUST equal caller's tenant_id
    glbs/<product>.glb
    fabric_maps/<series>/{diffuse,normal,roughness}.jpg
    thumbnails/<product>.jpg

Request-layer review of the existing code

The current app reviewed through the lens of network requests, read from source. Verdict: a wrap-and-scope job, not a rebuild.

Findings

Single asset choke point strong

Every GLB + texture routes through /api/s3proxy — tenant-scoping is a one-place change.

AI endpoints cleanly isolated strong

Adding auth + metering is a wrapper. Payload limits & graceful degradation already handled.

Zero authentication on any request critical

No Authorization header anywhere in src/. Must be added to all five request families + verified server-side.

The catalog is not a request critical

Products are a compile-time import. The unlocking request GET /api/catalog doesn't exist yet; insertion point is the hardcoded loadModel(CHAIR_GLB) in boot.

PolyHaven is a live consultation dependency high

Direct browser call bypasses the tenant boundary and degrades the demo if PolyHaven is slow. Bake maps into tenant S3 at onboarding.

Nine silent asset failures high

.catch(()=>null) turns a failed fabric into a blank grey mesh with no signal (materials.js ×7, room.js ×2).

04

API reference — every endpoint

Each endpoint documented individually: purpose, when it is called, request fields, response fields, errors and notes. ~17 endpoints we own (11 new · 5 hardened · 2 reused) plus 5 Supabase-handled. Every custom handler first calls _lib/auth — it verifies the token and derives tenant_id + role; a browser-supplied tenant id is never trusted. All requests carry Authorization: Bearer <token>.

Risks worth naming

Isolation must hold below the UI

RLS + proxy check are the real guarantee. Phase 3 is ordered early on purpose.

Open AI endpoints are an uncapped bill

Per-tenant quota is v1 scope, not a nice-to-have.

Segmentation is authored, not inferred

Each client's quality depends on the hand-authored part_map. Budget onboarding time.
