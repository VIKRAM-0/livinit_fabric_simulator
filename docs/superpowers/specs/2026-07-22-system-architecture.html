The three gaps that define this project

No identity — no login, user or client concept anywhere. No data layer — the catalog is compiled into JavaScript, not stored per client. No isolation — the asset proxy and every paid AI endpoint are open to anyone with the URL.

Figure 3 — Entity relationships. Every business table hangs off tenants.

The two fields that carry the product's intelligence

products.part_map — the authored mesh‑node → customizable‑part mapping. This is where "our team segments the sections" is captured, because arbitrary client furniture cannot be auto-classified reliably. fabrics.pbr_defaults — per-fabric roughness/sheen/scale so each finish renders true to material.

Note: usage_events is a thin local log; billing & caps ride Livinit's existing Stripe credits contract, not a bespoke meter.

05

Tenant isolation — the core guarantee

"Each account sees only its own assets" is enforced by two independent, server-side locks, both keyed on the tenant_id claim inside the signed-in token. Neither depends on the UI; either alone would stop a leak, and they never share a failure mode.

flowchart LR
  T["Signed-in token · tenant_id = A"]:::tok
  T --> Q1["DB query for another tenant's rows"]
  Q1 --> L1["LOCK 1 · RLS filter tenant_id = A"]:::lock
  L1 --> Z1["0 rows returned"]:::deny
  T --> Q2["Asset request for tenants/B/sofa.glb"]
  Q2 --> L2["LOCK 2 · proxy prefix check A ≠ B"]:::lock
  L2 --> Z2["403 · S3 never touched"]:::deny

Figure 4 — The same tenant_id claim guards both the database and the files.

The claim is set once, server-side, and never trusted from the browser

On sign-in, a Supabase hook stamps tenant_id + role into the JWT from the memberships table. Every endpoint re-derives these from the verified token — the client cannot assert which tenant it is. Hiding items in the UI is not part of the security model; it is only convenience.

Figure 5 — The eight-step onboarding pipeline.

  1. 1
    Intake client

    The client submits 2D images of the furniture to include, and a list of fabrics & finishes they want available.

  2. 2
    Account creation livinit team

    Staff create the tenant and the first client login in the staff console. Tenant starts in draft.

  3. 3
    3D modelling livinit team

    Each 2D product is converted into a clean 3D GLB model, sized to real-world scale.

  4. 4
    Segmentation livinit team

    Each customizable section (seat, back, arms, legs…) is written as the product's part_map — what makes "change this cushion's fabric" possible.

  5. 5
    Fabric setup livinit team

    For each finish, PBR maps are prepared or generated (the fabric-vision tool can seed values from a photo) and stored with type/hex/defaults.

  6. 6
    Upload & register system

    GLBs and maps upload to tenants/<id>/; product & fabric rows are written via the admin API.

  7. 7
    QA preview livinit team

    Staff preview as the tenant: every part accepts fabric, every finish renders true; fix the map if not.

  8. 8
    Go live system

    Tenant flips to active. Consultants log in and see exactly their catalog.

08

Asset storage & delivery

Binary assets stay in S3, reached only through the authenticated proxy so AWS credentials never leave the server and every byte is tenant-checked. Namespacing is the physical side of isolation.

s3://livinit-simulator/
  shared/                       # room shells, wood textures — any authed tenant
    glbs/room.glb
  tenants/<tenant_id>/          # gated: prefix MUST equal the caller's tenant_id
    glbs/<product>.glb
    fabric_maps/<series>/{diffuse,normal,roughness}.jpg
    thumbnails/<product>.jpg

Figure 8 — Bucket layout: shared read-only prefix + per-tenant private prefix.

Access

All reads via /s3proxy; prefix enforced per request. No public bucket URLs.

Caching

Vercel CDN edge-caches proxied assets; immutable keys per product version.

Uploads

Onboarding writes via short-lived presigned PUTs into the tenant prefix.

09

Security model

Beyond tenant isolation, the platform closes the two gaps the demo left open: unauthenticated endpoints and uncapped AI spend.

ConcernControl
AuthenticationSupabase Auth; no route serves data without a valid session. Boot itself is gated.
Tenant isolationRLS on every table + prefix check on every asset — both from the verified tenant_id claim.
Privilege separationOnboarding writes require role = staff; the service-role key is server-only, never shipped to the browser.
AI cost & abuseEvery Gemini call is authenticated, attributed to a tenant, and quota-checked via the credits contract before the paid request runs.
Secret handlingAWS, Gemini and service-role keys live only in server env vars. The frontend holds only the Supabase anon key + session.
TransportHTTPS end-to-end; short-lived presigned URLs for uploads; session tokens auto-refresh.
10

Deployment, stack & roadmap

Shipped as a dedicated Vercel project on its own domain, backed by a dedicated Supabase project — clean separation from Livinit's consumer apps.

Hosting

Vercel project → web.simulator.livinit.ai. Static SPA + serverless functions, CDN edge.

Identity & data

Dedicated Supabase project (Auth + Postgres + RLS). Own user pool — separate from consumer users.

Environments

Preview (per-branch) → Production. Supabase redirect URLs whitelisted per environment.

Server env vars

SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, AWS_*, S3_BUCKET, GEMINI_API_KEY.
