02 The gap, in one line

"See only your own assets" and "log in during consultations" are not features you add to this app — they are the platform layer it was never built with. Roughly 80% of this work is backend that does not exist yet.

Today — single-tenant demo
  • One shared, public asset set
  • No login — open to anyone with the URL
  • Catalog compiled into JavaScript
  • Any client could read another's files by guessing keys
  • Uncapped, unattributed AI spend
→
Target — per-client platform
  • Each account sees only its own furniture & fabrics
  • Login required; session drives everything
  • Catalog served per-tenant from a database
  • Isolation enforced in the database and the asset proxy
  • Per-tenant AI quota, logged and capped

03 Backend architecture

Standalone Supabase (Auth + Postgres + Row-Level Security) added to this Vercel app. The rendering engine stays untouched — we change where the catalog comes from and who is allowed to fetch it.

Reuse what Livinit already runs — don't rebuild it

Livinit's existing backend (api.livinit.ai) and web app already run Supabase auth (email, Google & Apple OAuth, password reset, sessions) and a real Stripe billing/credits system (BillingSnapshot + consume). We keep a separate identity silo — the simulator's users are client businesses, a different population from the consumer app — but we port the proven auth patterns and model AI metering on the existing credits contract rather than writing either from scratch. The one thing new to all of Livinit is the tenant/org model — see the strategic risk below.

Identity & access

Supabase Auth issues the session. A sign-in hook stamps two custom claims into every JWT, read server-side only — never trusted from the client:

// JWT claims after login
{
  sub:       "<user id>",
  tenant_id: "<uuid>",     // which client this user belongs to
  role:      "client"        // or "livinit_staff" for onboarding
}

A client maps to exactly one tenant in v1. livinit_staff unlocks the admin surface. Email/password + magic link; sessions refresh automatically.

Data model — Postgres + RLS

Every tenant-scoped table carries tenant_id. One RLS policy per table — tenant_id = (auth.jwt()->>'tenant_id') — is the true isolation boundary. Staff get a separate service-role path for onboarding.

Why part_map matters

Client furniture won't auto-classify — the current name-dictionary is tuned to three known products. The customizable sections your team segments during onboarding are stored here as an explicit mesh‑node → part‑name map, and applied at load time. This is the data form of "our team segments the sections."

Asset isolation & storage layout

One bucket, namespaced by tenant. The proxy compares the requested prefix against the caller's tenant_id — hiding assets in the UI is not isolation.

    thumbnails/<product>.jpg

AI gateway & cost control

The problem today

Anyone can POST to /api/generate. In a multi-tenant world with no cap, one client's live demo — or a scraper — runs up your Google bill with no attribution.

The control

A shared _lib/auth.ts verifies the JWT on every AI call and meters it through Livinit's existing credits contract (consume) — reusing billing that already exists rather than a bespoke counter. Spend becomes visible, capped, and billable per client.

Onboarding — staff admin

A Livinit-staff-only surface so a non-engineer can onboard a client end-to-end after the 3D models are built: create the tenant & login, upload each product GLB and author its part_map (reusing the existing viewer.html mesh preview), and register fabrics — seeded from the existing find-fabric analysis where useful. Writes go through the service role, itself guarded by a role = livinit_staff check.

04 Delivery plan

Security is wired in early, alongside auth — not bolted on later. Each phase ends with a gate that must pass before the next begins.

1

Data model & tenant backbone

The isolation boundary comes first. Schema, migrations, and RLS policies keyed on the tenant_id claim; the sign-in hook that stamps the claim.

Backend: Supabase project, 5 tables, RLS, custom-claims hook.
Gate: authenticated as tenant A, a query returns zero of tenant B's rows.
2

Auth & gated shell

Login page; boot blocks until a session exists; tenant_id read from the session. Logged-out users can reach nothing. Ported from web-pipeline's proven Supabase auth, not written from scratch.

Backend: Supabase Auth wiring (reused patterns), session guard, redirect config.
Gate: logged-out = login screen; no /api/* call succeeds pre-login.
3

Secure the proxies

The phase that actually protects clients from each other. Session check + tenant-prefix enforcement on s3proxy; auth + quota on every AI endpoint.

Backend: _lib/auth.ts, rewritten s3proxy, quota middleware.
Gate: tenant A requesting tenant B's key → 403; unauth AI call → 401; quota trips.
4

Tenant catalog (largest frontend change)

catalog.js becomes a runtime loader fed by /api/catalog; the product switcher goes data-driven; stored part_map replaces the guesswork.

Backend: /api/catalog. Frontend: loader + dynamic product UI.
Gate: two tenants see two different libraries; apply / room / render all still work.
5

Staff onboarding admin

Create tenant + login, register products with segmentation, register fabrics — enough that a non-engineer can onboard a client repeatably.

Backend: 3 admin endpoints + presigned uploads. Frontend: staff-gated admin views.
Gate: staff onboards "Acme"; the new client logs in and sees exactly Acme's assets.
6

Deploy to web.simulator.livinit.ai

New Vercel project + domain, env vars, Supabase redirect URLs, production smoke including a cross-tenant 403 check.

Ops: project, domain, secrets, auth redirects.
Gate: real tenant logs in on prod, customizes, renders; cross-tenant access is 403.

06 Risks worth naming out loud

Isolation must hold below the UIRow-level security and the proxy check are the real guarantee. If Phase 3 slips, one client can pull another's furniture by guessing keys. It is ordered early on purpose.
Open AI endpoints are an uncapped billPer-tenant quota is v1 scope, not a nice-to-have. Without it, a single demo or scraper can spend real money against your Gemini key.
Segmentation is authored, not inferredThe quality of each client's experience depends on the hand-authored part_map. Budget onboarding time for it; it is human work, not an algorithm.
Tenant model scope — decided: simulator-onlyLivinit has only ever modeled individual users. Rather than make orgs a company-wide backend primitive now, the tenant/org model lives only in the simulator (own Supabase, RLS-enforced, zero blast radius on the core backend). If B2B becomes strategic later, promoting orgs to the shared backend is a bounded migration — not a rewrite. The seam is kept clean for that.
Confirm the base repoThis clone drifts from its own architecture doc (no bed, missing search endpoints). Lock which snapshot is canonical before building, or Phase 4 will be built against the wrong catalog.
Per-client branding is out of scope (for now)"Dedicated experience" hints at each client's own logo/theme. The database reserves a branding column, but the UI is deferred unless you ask — flagging so it isn't an assumed deliverable.
